### Native backend blocker: modal shortcut repeats after release

Reproduction: start the native backend, press/release Ctrl+O, then cancel or close the repository dialog. The dialog
can reappear immediately; extra instances can also appear beneath its folder picker. The protocol trace records
both O key-down and key-up (Wayland key 24) before the dialog is mapped. Repeated dialog creation continues without
new physical key presses. This was reproduced with Hyprland's physical-key injection, separately from `wtype`'s
custom keymaps, which do not reliably map text input to Avalonia physical keys.

The 12.1.3 backend source explains the behavior:

- [`WindowImplBase.cs`](https://github.com/AvaloniaUI/Avalonia/blob/12.1.3/src/Avalonia.Wayland/WindowImplBase.cs):
  `DispatchInput` returns for a disabled modal owner **before** `HandleKeyboardDispatch`, dropping key-up and
  keyboard-leave processing that should stop its repeat timer.
- [`WindowImplBase.Keyboard.cs`](https://github.com/AvaloniaUI/Avalonia/blob/12.1.3/src/Avalonia.Wayland/WindowImplBase.Keyboard.cs):
  `OnKeyRepeatTick` invokes `Parent.Input` directly without checking `Parent.IsEnabled`. The stored Ctrl+O keeps
  entering the app even while its owner is disabled, and remains active after the dialog closes.

The proper backend fix should stop repeat when a window is disabled or loses keyboard focus and process releases
while disabled, without starting repeats for new input on a disabled window. This pass does **not** patch Avalonia
internals or claim that issue fixed. Native Wayland stays opt-in until an upstream fix is available and rechecked.
Evidence: `logs/native-protocol.log` and the pinned source copies in `upstream/`. No upstream issue was posted.

This pass did not repeat the seven external-tool merges, all Git workflows, drag/drop, multi-monitor scaling, or
Windows/macOS QA. Avalonia's native Wayland windows also advertise no app ID here, so compositor class-based rules
cannot identify them normally; that is another backend limitation rather than a tested app-side fix.

## Local Avalonia source patch (2026-09-26)

At the owner's request, upstream tag `12.1.3` was cloned to `/home/julius/avalonia-wayland-fix`, including its two
submodules. A private .NET SDK 10.0.201 was installed under `/tmp/ge-wayland-patch-20260926/dotnet` to meet upstream's
SDK requirement. The patch is committed **locally** on `codex/wayland-modal-key-repeat` at
`fa5cfdcb672dc1c615848bac71f9ae5b47c60328`, based on `8eeda4f6f546165b3f72e63c9f42247abb306905`.
The bug was previously submitted as [AvaloniaUI/Avalonia#22317](https://github.com/AvaloniaUI/Avalonia/issues/22317);
no fix PR, follow-up comment or package was published in this pass.

The two-file backend fix cancels the sink's repeat timer immediately when its owner is disabled, processes keyboard
release/focus-loss cleanup before rejecting disabled input, prevents disabled key-down events from starting repeat,
and guards repeat ticks against disabled/disposed sinks. There is no reflection or in-memory workaround in Git
Extensions. Eight Linux sink regressions cover disabled key release/leave, disable-and-reenable without release,
